    Experiment tracking with MLflow · Part 1

    Giving the campaign model a history

    Every training run recorded with its parameters, its metrics, its files, and its code — in one place you can search.

    Store: SQLite backend + artifact folder Library: MLflow 3.16.1 Read time: ~18 min

    Before — one file, one memory

    model_meta.jsonlatest run only
    study.dbscores, no models
    git logwhatever got committed
    →

    After — a row per run

    run 3f9a12elogreg-baseline
    run 7c02af4hgb-early-stopping
    run 1e88bd0campaign-train

    A trained model file can only ever describe one run: the last one. Before this stage, the campaign project has no way to answer a simple question — what did the random forest score on the holdout, and was that before or after the pipeline changed?

    The service the project already ships reads a file called model_meta.json. Train again, and the old description is gone — overwritten by the new one. An Optuna study sits alongside it, remembering the scores from sixty tuning trials, but with no fitted model behind any of them and no commit attached to say which code produced them. Git holds a version of the metadata file for every commit, but only for the commits somebody happened to make, and a commit message rarely explains why a number changed.

    An earlier stage of this project made a promise about this gap. It wrote a config, a random seed, a hash of the training data, and the library versions into a JSON file beside the model, and said a tracking tool would later do the same thing automatically, and at scale. This is that tool. MLflow Tracking records every run in a small database: its parameters, its metrics, its tags, its files, and the fitted model itself, all living in one place a person can search, sort, and open in a browser.

    The story carries on from where the project left off — same bank, same calls, same model. It simply gains a memory.

    1

    The gap tracking fills

    The quickest way to see what's missing is to ask the project about its own past.

    What the service's own file can say

    The metadata file names the family, the one setting it used, and the score it got — a good record of one run. There's no second run in it, because there was never room for one.

    What the tuning study can say

    The Optuna study tried all three model families, and it remembers a cross-validated score for every trial it ran. But each row is only a number: no fitted model sits behind any trial, there's no holdout score, and nothing ties a trial back to the code that produced it. Asked how the best random forest actually did on the test set, the study has no answer — nothing ever fit that forest on the full training set.

    What Git can say

    The metadata file is committed, so its history in Git is a history of runs — or at least of the runs somebody chose to commit. Walking that history turns up five versions of the file. Four of them record the exact same model, with the same 0.8166 score, because those commits changed the metadata for unrelated reasons. The oldest version belongs to a different project entirely — the churn model this repository started life as. Any run that was trained and never committed left no trace at all.

    The gap

    Git versions files well and results badly. A commit can carry one run's numbers forward, but it can't answer “which of the last twenty runs was best, and what was different about it?”

    That's the whole shape of this session: moving from one hopeful filename per attempt to a table of runs that anybody can open, sort, and search.

    A folder of hopeful filenames, next to a store where every run keeps its own row.

    2

    What a tracking store keeps

    The vocabulary means more once you've seen the rows it describes. A single run through the plainest model in the project — a logistic regression with its default settings — is enough to write three things down: which family it was, the one setting it used, and the score it got.

    scratch/explore_tracking.ipynb
    import mlflow
from sklearn.metrics import roc_auc_score
from campaign.pipeline import build_pipeline

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("term-deposit")

with mlflow.start_run(run_name="logreg-baseline") as run:
    params = {"C": 1.0}
    mlflow.log_param("family", "logreg")
    mlflow.log_params(params)

    pipeline = build_pipeline("logreg", params).fit(X_train, y_train)
    auc = roc_auc_score(y_test, pipeline.predict_proba(X_test)[:, 1])
    mlflow.log_metric("test_roc_auc", auc)

    Three calls do the work. set_tracking_uri says where runs are stored — here a SQLite file called mlflow.db in the repository root. set_experiment names the group this run belongs to, creating it the first time it's used. start_run opens a run, and the with block closes it when the block ends, even if the code inside raises an error.

    mlflow.db turns out to be an ordinary SQLite database — nothing about it is special to MLflow, so any SQLite client can read it directly. Reading those rows back gives the vocabulary a definition apiece:

    Experiment

    A named group of runs about one problem. MLflow always keeps a Default experiment for runs that were never given one — here the real group is term-deposit, the same name the Optuna study uses, because it's the same problem.

    Run

    One execution of the training code. It has an id, a name you chose, and a status — FINISHED means the with block ended without raising.

    Parameter

    Something decided before training. Logged as text no matter what you pass in — C comes back as the string '1.0', not a number. A random seed is a parameter.

    Metric

    Something measured. Stored as a number, together with a step — zero here, since the score was only logged once. A training time is a metric.

    Tag

    A searchable label. None were logged by hand, yet four appear — MLflow adds its own, recording who ran the code and from which file. “Reviewed by the risk team” is a tag.

    Backend store & artifact store

    Two stores sit behind all of this. The backend store is mlflow.db, holding every parameter, metric and tag row. The artifact store is a folder, mlruns/, holding files such as plots and fitted models once a run logs any.

    Anything the Python API can find, the browser UI can show — they read the same files.

    Two ways to reach a run

    Every mlflow.something call so far has acted on whichever run is currently open. That's convenient inside a with block, and useless once it ends — no run is open any more. MlflowClient is the other door in: an object that talks to the same store but names the run it means by id, so it can read or change any run at any time, including one that finished an hour ago.

    Easy to get wrong

    Call mlflow.set_tag after a run has ended, and MLflow doesn't tag that run — it quietly starts a new, empty run with a random name and tags that one instead. For a run that has already finished, reach for MlflowClient() and its id.

    One more habit from older tutorials is worth naming here: setting set_tracking_uri("file:./mlruns") stores runs as plain folders instead of a database. On a current, pinned install this now raises an error outright rather than quietly working — MLflow wants a real database, with mlflow migrate-filestore offered to move any old folder-based runs across.

    3

    Parameters, metrics, and tags behave differently

    All three kinds of record look alike in code — each is one log_ call. They behave differently once they're stored, and that difference decides what belongs in each.

    What each kind answers, and whether it can change later
    KindAnswersCan it change after logging?
    ParameterWhat did you decide before training?No — fixed once logged, stored as text
    MetricWhat did you measure?Yes — by adding values at new steps
    TagWhat do you want to search by?Yes — it can be overwritten

    A parameter is fixed on purpose: a run's parameters are meant to be the settings that produced its results, and a setting that can change afterward is no longer a record of anything. Logging C twice into the same run — a default followed by the value actually used — raises an error. The fix is to decide the value first and log it once; two genuinely different values means two separate runs.

    A metric can grow into a curve

    A metric can be logged many times within one run, each with its own step number, and MLflow keeps every value — which is how a training curve gets recorded. The gradient-boosting family can stop early: it holds back part of the training set and scores the model on it after every boosting iteration, so that curve is logged one step at a time as it trains, with early_stopping=True, validation_fraction=0.2, n_iter_no_change=20, learning_rate=0.05, and max_iter=400.

    48 values logged for validation_roc_auc — one before the first tree, one after each of 47 boosting rounds.

    Step zero is the score before any tree was added — exactly 0.5, the ROC AUC of a model that gives every customer the same score, which is why there's one more value than there were boosting iterations. The best validation score lands at iteration 27; training then runs for another twenty iterations regardless, because that's what n_iter_no_change is waiting out. For a model that trains for hours, logging the curve as it goes is also how a bad run gets noticed and stopped early.

    A tag is how you find it again

    A tag can be set after a run has finished, and set again later — which makes it the right place for things only known afterward: which runs were baselines, which went to review, or a short note explaining why a run exists. MLflow reserves one tag name, mlflow.note.content, and shows whatever it holds as the run's description at the top of its page.

    Comparing runs

    One run is a record. Tracking starts paying for itself once there are several runs of the same problem to line up against each other. Seven hand-picked configurations — two or three per model family, including the tuning study's own best — each log a cross-validated score on the training set and a score on the holdout, so the two can be compared afterward.

    The study's configuration wins on both columns. Lower down the two columns disagree: default gradient boosting is second by the cross-validated score, while the deeper forest is second on the holdout. Which column a leaderboard sorts by is therefore a real decision, and it has a right answer — sort by the score a run was chosen on (the cross-validated one), and read the holdout score only as a check. Sorting by the test score instead quietly spends the holdout; with seven runs that costs almost nothing, but with two hundred, the top test score is partly just the luck of which run happened to fit those particular rows.

    A small, SQL-like filter language

    Runs are searched by naming a field with its kind and key — params.family, metrics.cv_roc_auc, tags.stage — and comparing it to a value:

    filter examples
    "params.family = 'hgb' AND tags.stage = 'sweep'"
"metrics.cv_roc_auc > 0.795"          # order_by=["metrics.cv_roc_auc DESC"]
"params.family = 'rf'"                # order_by=["params.max_depth DESC"]

    The first two behave exactly as expected. The third does something quieter and wrong — and it doesn't complain either.

    WHY IT GOES WRONG — PARAMETERS ARE STORED AS TEXT
    order_by max_depth DESC
    what it should mean
    rf-depth16-leaf20 · depth 16
    rf-depth8 · depth 8

    Sorted as text, “8” comes after “16” — the same way “ab” comes before “b”. Toggle above to see the depth-8 forest jump above the depth-16 forest even though the query asked for deepest first.

    Parameters accept =, !=, LIKE, ILIKE, and the two IS NULL checks — never > or <. Both behaviors come from the same fact: parameters are strings. Ranking or thresholding on a setting means logging it as a metric as well, or comparing values in pandas after search_runs returns them.

    5

    Artifacts, and the model itself

    Parameters and metrics are small values. Most of what a run leaves behind is files — plots, reports, the metadata a service reads, and the fitted model. MLflow calls these artifacts and keeps them in the mlruns/ folder, one directory per run. log_figure, log_dict, and log_text write a figure, a dictionary, or a string straight into a run's artifacts — nothing is saved into the project itself, so there's nothing to clean up and no chance of logging yesterday's plot by mistake.

    The threshold decision, made visible

    A confusion matrix at the model's chosen decision threshold, beside one at the default 0.5, is exactly the kind of evidence worth keeping alongside a run.

    CONFUSION MATRIX AT TWO THRESHOLDS · 1,160 subscribers in the test set
    People called
    Subscribers reached

    For a tool that insists on writing its own files — a report generator that expects an output folder, say — pointing it at a temporary directory and then calling mlflow.log_artifacts(folder) keeps only MLflow's copy; the temporary folder is deleted once the block ends.

    What MLflow asks you to trust before it saves a model

    mlflow.sklearn.log_model saves a fitted estimator as an artifact, together with a description of how to load it back — but not as a pickle. MLflow now saves scikit-learn models with skops, a format that stores a model as data rather than as code to execute. A pickle runs whatever code the file contains when it's loaded; that's fine for a file you built yourself, and not fine for a model downloaded from a shared server.

    What skops needs named before it will load a model

    skops still has to rebuild a few types that could be abused if a file were tampered with, and it refuses to do so silently — each one has to be named explicitly, so that a person has actually looked at what's being trusted.

    Model familyTrusted types it needs
    Gradient boostingnumpy.dtype, TreePredictor
    Random forestthe above, plus sklearn.tree._tree.Tree

    Pickles remain available with serialization_format="cloudpickle" — a fair choice for a model only ever loaded by its own author, made knowingly rather than by default.

    Once logged this way, a model can be reloaded from nothing but its run id — runs:/<run id>/model is an address anyone with access to the store can use. Reloaded and checked against the model still in memory, every one of 10,297 test predictions matches exactly. Since MLflow 3, a logged model gets its own id and folder under mlruns/<experiment id>/models/, complete with a requirements.txt pinning the library versions it was saved with — the run simply links to it.

    6

    What goes wrong quietly

    None of the following raise an error the moment they happen. Each produces a store that looks fine and gives the wrong answer later — usually to somebody else.

    1A failed run can still rank at the top›

    A model-logging attempt can fail after its metric was already logged, leaving a run marked FAILED that nonetheless has a perfectly good score — and no model behind it. Asking for “the best run” by test score with no other filter, four runs can tie at the top, one of them the crashed one. Filtering on attributes.status = 'FINISHED' only half-fixes this: finished just means the code didn't raise, and a run can finish cleanly without ever logging a model. Look up a run to use its model by filtering on the thing that produced models on purpose — a tag a training command sets — rather than on the best number in the experiment.

    2Run names repeat — only the id is unique›

    Nothing stops two runs from sharing a name. Re-running a training cell or a script a second time is the usual way this happens: two runs both called logreg-baseline, with identical scores, but only one carrying the stage: baseline tag added afterward. Filtering by that tag finds one run; searching by name finds two, with nothing to say which is the one people have actually been discussing. Refer to runs by id whenever it matters — in a message, a ticket, or a config file — since the run id is the only field MLflow guarantees is unique.

    3A relative store path silently gives you an empty store›

    sqlite:///mlflow.db is a relative path, resolved against whatever directory the process starts in — not against the repository root. Point MLflow at that URI from inside a subfolder and it creates a brand-new, empty database there without complaint, reporting only the default experiment. Every earlier run is still perfectly safe at the repository root; from this process, though, none of it exists. This is by far the most common “my runs have disappeared” report, and it happens to the UI in exactly the same way. The fix is to build the store path from the project root in code, or to set MLFLOW_TRACKING_URI in the environment, which every MLflow process reads.

    7

    The training command records itself

    Everything so far ran inside an interactive session — good for learning the calls, bad as a habit. The runs worth keeping are the ones the project's own command produces, so that's where tracking belongs. A new file, campaign/track.py, runs the same training entry point the service already uses and then records what it produced as one run. The original training script isn't edited at all, so the tracked command and the untracked one can never disagree about how a model was built.

    campaign/track.py
    def main():
    mlflow.set_tracking_uri(TRACKING_URI)
    mlflow.set_experiment(EXPERIMENT)

    with mlflow.start_run(run_name="campaign-train") as run:
        train.main()
        meta = json.loads(train.META_PATH.read_text())

        mlflow.log_params({"family": meta["family"], **meta["params"]})
        mlflow.log_params({
            "decision_threshold": meta["decision_threshold"],
            "study_trials": meta["study"]["trials"],
            "sklearn_version": meta["sklearn_version"],
        })
        mlflow.log_metrics(meta["metrics"])

        # MLflow records the commit by itself. It does not record whether the
        # working tree matched that commit, so that part is still ours to log.
        mlflow.set_tags({
            "stage": "training",
            "git_dirty": str(meta["git"]["dirty"]),
        })

        mlflow.log_artifact(str(train.META_PATH))

        pipeline = joblib.load(train.MODEL_PATH)
        mlflow.sklearn.log_model(
            pipeline, name="model", input_example=example,
            signature=infer_signature(example, pipeline.predict_proba(example)),
            pyfunc_predict_fn="predict_proba",
            skops_trusted_types=TRUSTED_TYPES,
        )

    Nearly every call here already appeared earlier in this reading. The one new argument, pyfunc_predict_fn="predict_proba", makes the logged model answer with probabilities, since the service applies its own threshold on top. Most of the parameters and all of the metrics are read straight out of the metadata file rather than recomputed — that file is already the contract the service reads, so the run records the exact same numbers the service will report.

    What gets captured without being asked, and what doesn't

    Run as a script from inside a Git repository, MLflow records the commit, the branch, and the remote entirely by itself. Run from an interactive session instead, the recorded source is the session itself — and there's no commit at all, because MLflow can't tell which cells ran, or in what order. That's the practical reason the runs worth keeping come from a command, not a notebook.

    MLflow records which commit, but nothing about whether the working tree still matched it — which is exactly what the git_dirty tag exists to add. Running the training command twice in a row, from the same commit, produces two runs with identical scores; the second one alone is tagged dirty, because the first run's own outputs — the fitted model file and its metadata — had already changed on disk by the time the second run started. The changed files are outputs rather than code here, so the scores are unaffected, but the tag is what lets a clean rebuild be told apart from “somebody edited the pipeline and didn't commit it.”

    8

    Where tracking stops

    This stage gives the model a history. Four things it deliberately leaves out mark the edges of what tracking alone does.

    NOT RECORDED — WHICH RUN IS IN PRODUCTION

    The store holds many runs and says nothing about which one a service is actually serving. Naming a model, giving it versions, and promoting one to production is the job of a model registry — a later stage of this course.

    STILL SEPARATE — THE TUNING STUDY

    The Optuna study and the tracking store sit side by side, but a trial still isn't a run. Logging every trial as a child run, with MLflow capturing scikit-learn fits automatically, is where the next tracking session starts.

    LOCAL ONLY — THE STORE LIVES ON ONE LAPTOP

    mlflow.db and mlruns/ are both git-ignored, so nobody else can see these runs. A team instead runs one shared tracking server with a real database and a shared bucket for artifacts — the code doesn't change, only the URI does.

    NOT CONNECTED — NOTHING IS SERVED FROM MLFLOW

    A logged model can be loaded by run id, and MLflow can serve it over HTTP too. The FastAPI service still loads its own model file directly — comparing the two ways of serving is a question for later.

    An honest word on cost

    For a project trained once a month by one person, a committed metadata file is enough, and a tracking server is ceremony. Tracking earns its keep once the number of runs outgrows anyone's memory, or once more than one person is training the same model — which is why, for now, the store here is a single file rather than a server.

    9

    Summary

    A model file can describe one run. A project needs to describe all of them, and before this stage it couldn't: the metadata held only the latest run, the tuning study held scores with no models or code behind them, and Git held whatever anyone happened to commit — sometimes another project's numbers entirely.

    MLflow Tracking fixes that with a small, plain structure. An experiment groups runs about one problem. A run records parameters, decided in advance and fixed once stored as text; metrics, measured and able to grow into a history across steps; and tags, searchable and free to change. Files and the fitted model go into an artifact folder beside the database. All of it lives in mlflow.db and mlruns/, and the browser UI is a view over those same files — never a second copy.

    The pinned library version matters more than usual here: the older folder-based store now raises rather than quietly working, and scikit-learn models are saved with skops, which requires naming the types you trust. Both changes break old code loudly, which is the better way for a breaking change to fail.

    The quiet failures worth remembering
    A failed run can still rank.It can hold a good metric and no model, and a best-run lookup will sometimes pick it.
    Run names repeat.Only the run id is unique.
    A relative store path follows the working directory.The wrong folder gives an empty store, with no error.
    Parameters are text.They sort as text, and can't be compared with >.

    And one judgment call worth repeating: sort a leaderboard by the score a run was chosen on, and read the test score only as a check — otherwise the holdout quietly stops being honest.

    Finally, the runs worth keeping come from a command, not an interactive session. Run as a file, the training command now records its own commit without being asked; track.py adds the one thing MLflow genuinely can't see on its own — whether the working tree was clean.
